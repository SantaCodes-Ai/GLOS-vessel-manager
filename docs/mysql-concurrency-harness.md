# MySQL concurrency harness — Phase 14B-5A

**Historical Phase 14B-5A report.** Phase 14B-5B now adds the explicit three-record
fixture lifecycle and fixed run-scoped worker verification. See
[the current lifecycle instructions](mysql-concurrency-fixture-lifecycle.md) for the new
command, commit tracking and failure boundaries. Statements below about unavailable
fixture commands describe the earlier phase. Its verification results are retained.

This is separate test-only infrastructure. No application behaviour, existing test base,
profile, migration, MySQL grants or business records were changed. No live command below
was executed during implementation.

## Entry points and current scope

`scripts/mysql-concurrency.php` requires an explicit operator and exactly one mode:

```sh
# Proposed first live check, only after separate approval:
php scripts/mysql-concurrency.php --inspect --operator="Ivan"

# Proposed first worker test, also requiring separate approval:
php scripts/mysql-concurrency.php --probe --operator="Ivan"
```

Inspect verifies the baseline without starting workers. Probe starts exactly one independent
read-only PHP worker and verifies the clean baseline again. Neither mode creates fixtures,
executes a business race, boots the company application or invokes cleanup. There is no
business-workload registry, fixture creation command or live cleanup command in this phase.
Do not use PHPUnit `--parallel`, schema credentials, or the schema preparation script.

The scripts deliberately do not load `.env`. The existing private runner profile must be
present with its existing private permissions, testing identity and ownership token. Existing
ambient override/cache checks still apply; do not disable them to get a command to run.

## Coordinator and worker trust

The coordinator uses the existing `Runtime::lock` and `Runtime::databaseMutex` unchanged.
Both mutexes are retained for the process lifetime. `Guard::prepared(..., true)` verifies
runner grants, actual MySQL identity, ownership, server UUID, source migration baseline,
schema fingerprint and clean baseline before work. A separate verified runner connection
is used by the native adapter. It never connects to the development database.

The worker script accepts no command-line parameters. A newline-terminated private stdin
message supplies a random 256-bit capability and private lease path. The journal/lease
folder is random and mode 700; files are mode 600. The lease stores only a capability hash,
coordinator PID, advisory-lock owner connection ID, expiry and protocol/database identity.
The capability is never put in command arguments, journals or output.

Workers verify the lease, capability, living coordinator PID, expiry, existing guards and
current server mutex owner before reporting success. They do not acquire or compete for
the coordinator's server mutex. Their delegated authority is a read-only probe only;
committed-fixture participation is intentionally not enabled. There is no raw SQL or DDL
API exposed by the worker entry point. The restricted runner's grants remain essential.
This is protection against mistakes and unintended invocation, not isolation from malicious
PHP code or another process with the same OS identity and access to the private credentials.

## Bounds, barriers and outcomes

Worker authorisation input has a two-second deadline and an 8 KB limit. Worker processes
have a ten-second timeout and are stopped before recording `stopped`. Any timeout or
failed outcome blocks automatic cleanup, even after the worker has stopped. A fixed probe
is the only current workload; no worker descendants are allowed.

`Barrier` provides bounded socket/pipe messages using `stream_select` and monotonic deadlines,
including deadlines for partial messages. It does not use sleep-based coordination. Future
scenarios must identify exact before/after-lock barrier points and one-shot retry behaviour.

The journal accepts bounded attempts and safe outcome categories, including deadlock 1213,
lock timeout 1205, commit and rollback. It does not store SQL exceptions, passwords, account
password hashes, ownership tokens, PDF contents or raw database rows. Full rows are compared
in memory; only fingerprints are journalled. Actual service retry observation is future work.
The native cleanup transaction uses a fixed session `innodb_lock_wait_timeout = 3`; no global
settings are changed. Child process deadlines bound probe metadata reads. No application
notifications are generated by the current standalone PDO workers; mail/notification fakes
and the existing isolated application bootstrap must be installed before future business
workloads are enabled. No real SMTP or database queue is used here.

## Fixture journal and cleanup implementation

A run journal records its operator, random run ID, fixture table/ID/fingerprint, exact owned
file paths, worker events and cleanup progress. Root fixture claims require run-specific
fictional identifiers:

- Users: email ending `+<run-id>@example.test`.
- Vessels and certificate types: name `Concurrency <run-id>`.
- Dependent rows: already claimed parent IDs. Assignment claims require both parents;
  audit claims require owned actor and target/applicant IDs.

Only eight explicitly listed business tables can be claimed. Baseline, cache, session and
queue tables cannot be claimed. Fixture creation is not implemented or authorised yet.
Future workloads need durable planned identifiers before committing inserts and explicit
recording of newly created IDs; an uncertain commit must stop for manual review.

`Coordinator::cleanup` is library code only, not a command. It requires retained mutex
ownership, stopped successful workers, an exact match between all business rows and the
journal, and an exact match between actual private storage files and recorded paths.
Unexpected/missing/changed rows, untracked files, symlinks and changed storage roots refuse
cleanup before any deletion. File paths cannot be absolute, contain traversal, or name
non-PDF files.

The native adapter rechecks the snapshot under row locks in one transaction. It uses only
`DELETE FROM <fixed-table> WHERE id = ?`, child first, checking affected row counts. It
checks the approved baseline before commit and retains FK enforcement. Ownership, migration
and privilege-lock records are excluded. Mutex ownership is checked again before commit.
The coordinator verifies the baseline again after commit, then deletes exact journalled
private files. Any failure retains the journal and requires review; there is no reset,
truncate, broad delete, automatic retry/repair or startup recovery sweep.

A committed cleanup followed by a crash/file-deletion failure can leave test-only files.
Partial cleanup state must be reviewed manually; rerunning cleanup is not a recovery plan.
Journals are intentionally retained and not removed by shutdown handlers. Atomic journal
replacement and fsync reduce partial-write risk but do not promise recovery from every
OS/storage failure. No independent-process commit can be undone by a parent's rollback.
Auto-increment gaps are expected; never reset counters to restore a baseline.

## Unchanged behaviour policies

- In-flight administrator revocation remains unchanged. A request authorised before
  demotion/deactivation can finish in paths without a fresh transactional actor check.
- No automatic certificate deduplication or request idempotency is introduced.
- Staff edits/assignment updates retain last-writer-wins behaviour; competing submissions
  can overwrite an earlier edit. No optimistic concurrency token is added.

## Verification and next approval boundary

Mock-based unit tests use fake PDO/guard/process/backend objects and private temporary files.
They do not read real profiles or connect to MySQL. Existing identity, schema and baseline
rejection tests remain separate and unchanged. The default suite still uses SQLite memory
and the existing MySQL suite still uses its managed rollback lifecycle.

Separate approval is required before running either live command, creating committed
fixtures, enabling business workers, invoking cleanup against MySQL, adding concurrency
scenarios or process-crash tests. No schema changes or expanded grants are proposed.

After the read-only probe is approved and passes, the next implementation should add a
single-worker committed-fixture lifecycle with exact journal/cleanup validation, before
attempting two-worker renewal or decision races. A new run-scoped allowlist guard will be
needed for committed fixtures; the current clean-baseline worker check must not simply be
removed. The existing `MySqlTestCase`, SQLite guard, parallel-test prohibition and suite
mutexes must remain unchanged.
